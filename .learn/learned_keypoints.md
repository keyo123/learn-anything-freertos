## 1. 任务创建与删除

### 💡 核心机制
* **动态内存分配**：`xTaskCreate()` 函数在堆（Heap）上自动为任务分配任务控制块（TCB）和任务堆栈。
* **堆栈高水位监测**：使用 `uxTaskGetStackHighWaterMark(NULL)` 监测**当前任务自启动以来历史最小空闲堆栈大小**（以“字/Words”为单位）。若返回 0 则表明堆栈已溢出；若余量过大则说明内存被浪费。
* **自我销毁**：任务调用 `vTaskDelete(NULL)` 标志着任务的生命周期结束，自我销毁并移出调度器。

### ⚠️ 避坑指南
* **空闲任务内存回收**：动态创建的任务在自我删除后，**其 TCB 和堆栈的物理内存回收是由空闲任务 (Idle Task，优先级 0) 异步完成的**。
* 如果系统里有一个优先级 $\ge 1$ 且没有阻塞延时（如 `vTaskDelay`）的死循环任务独占 CPU，会导致空闲任务被饿死，导致系统内存迅速耗尽并发生 Crash。

## 2. 中断安全 API

### 💡 核心机制
* **FromISR 后缀**：在中断服务程序（ISR）中，必须使用带 `FromISR` 尾缀的内核 API（如 `xSemaphoreGiveFromISR`）。
* **实时任务切换（Yield）**：
  * 中断安全 API 会带有一个参数 `BaseType_t *pxHigherPriorityTaskWoken`。当该调用唤醒了一个高优先级任务时，内核会将其修改为 `pdTRUE`。
  * 退出中断服务前，必须调用 `portYIELD_FROM_ISR(xHigherPriorityTaskWoken)` 强制触发挂起的中断（PendSV），使高优先级任务在退出中断的瞬间**立即抢占运行**，保证实时相应。
* **硬件优先级界限**：
  * `FromISR` API 仅能从物理优先级**等于或低于** `configMAX_SYSCALL_INTERRUPT_PRIORITY` 的中断中被调用（在 STM32 优先级组4下，中断抢占优先级数值必须 $\ge 5$）。
  * 优先级更高的硬实时中断不能调用任何 FreeRTOS API，但它们绝不会被内核延迟，响应极其迅速。

### ⚠️ 避坑指南
* **中断调用空指针防崩溃**：在中断中操作任务句柄（例如通过 `xTaskResumeFromISR` 唤醒任务）时，**必须提前进行非空校验**（如 `if (xTaskHandle != NULL)`）。如果对空句柄进行操作，会触发 FreeRTOS 内部的 `configASSERT` 导致系统崩溃挂起。

## 3. 递归互斥量

### 💡 核心机制
* **可重入锁**：允许同一个任务在不释放锁的前提下，**多次成功获取（Take）同一把锁**而不发生自我死锁。主要用于多层函数嵌套调用或递归函数保护共享资源。
* **嵌套计数器**：递归互斥量内部维护一个计数器。同一个任务 `Take` 了多少次，就必须配对 `Give` 多少次。
* **完全释放**：只有当该任务的释放次数与获取次数相等，计数器清零后，锁才会真正归还内核，其他就绪任务才能获取。

### ⚠️ 避坑指南
* **锁扣留饥饿**：如果获取了 3 次但只释放了 2 次，该锁将永远被此任务（即使此任务已经删除）扣留。此时其他尝试获取此锁的任务（如 `Observer` 任务）会被无限期挂起直至发生超时（Timeout）。

## 4. 计数信号量

### 💡 核心机制
* **资源池管理**：创建时定义最大容量和初始资源数 `xSemaphoreCreateCounting(uxMaxCount, uxInitialCount)`。
* **多资源控制**：每次 `Take` 使计数值减 1，每次 `Give` 使计数值加 1。当计数值为 0 时尝试 `Take` 的任务将进入阻塞。
* 典型应用场景为**停车场车位管理**或**生产者-消费者缓冲区资源控制**。

## 5. RTOS vs GPOS

* **RTOS (如 FreeRTOS)** 追求的是 **确定性（Determinism）**。调度算法为严格的优先级抢占式。它的临界区极短，在最坏情况下的响应延迟是微秒级且可预测的。
* **GPOS (如 Linux/Windows)** 追求的是 **高吞吐量（Throughput）和公平性（Fairness）**。内核中频繁存在非抢占区和自旋锁，即使将某个任务设为最高优先级，也无法保证微秒级的响应，容易发生不可靠的延迟抖动（Jitter）。

## 6. 任务通知 (Task Notification)

### 💡 核心机制
* **轻量级同步/通信**：任务通知属于**点对点**通信（必须指定目标任务句柄）。因为其 32 位通知值及状态直接存放在任务控制块（TCB）中，**无需额外创建内核对象**，因此具有 **RAM 零开销**，且速度比传统队列/信号量**快 45%**。
* **二值/计数信号量替代**：使用 `xTaskNotifyGive` / `ulTaskNotifyTake` 可实现极简同步。
* **高级事件/数据传递 (Actions)**：
  - `eSetBits`：对接收任务通知值执行按位或 (OR)，可用二进制位代表不同的警报/状态，效果等同于**事件组 (Event Group)**。
  - `eSetValueWithOverwrite`：覆写接收任务通知值，用以传递 32 位具体采样/数据值，效果等同于**单深度邮箱队列 (Queue)**。
* **接收解码与清除 (`xTaskNotifyWait`)**：
  - 支持设置 `ulBitsToClearOnEntry` (进入等待前清除位) 和 `ulBitsToClearOnExit` (接收成功退出前清除位，常用 `0xFFFFFFFF` 全清零)。
  - 从传出参数 `pulNotificationValue` 读取接收到的通知值，并通过按位与 (`&`) 判定状态位或读取具体值。

### ⚠️ 避坑指南
* **单接收者局限**：不能用于多任务同时等待同一个事件（非多对多广播），只支持点对点。
* **中断向外单向性**：中断可以通过 `vTaskNotifyGiveFromISR` 唤醒任务，但任务无法给中断发通知。

## 7. 队列 (Queue)

### 💡 核心机制
* **先进先出 (FIFO)**：默认遵循 FIFO 规则。支持通过 `xQueueSendToFront` 从头部插入数据。
* **值拷贝 (Copy by Value)**：发送数据时由内核进行物理拷贝，即使原局部变量生命周期结束，数据依然在队列中安全保留。但对于大结构体，应传递指针（引用传递）以降低 CPU 开销。
* **双向阻塞**：支持读写双向阻塞超时。当队列为空/满时，读/写任务自动被加入到 `xTasksWaitingToReceive`/`xTasksWaitingToSend` 等待列表并进入挂起状态，不占用 CPU，直到被相应的读写操作自动唤醒。

### ⚠️ 避坑指南
* **中断调用安全**：在中断服务程序（ISR）中禁止调用普通的 `xQueueSend`/`xQueueReceive` 等可能会引起阻塞的 API。必须使用带 `FromISR` 后缀的中断安全版本，且设置超时（Timeout）为 0。
* **引用传递的内存安全**：若在队列中传递指针，必须确保指针所指向的物理内存是非栈区（例如全局变量、静态变量或动态申请且在处理完后手动释放的 Heap 空间），防止接收方读取到已被回收或改写的脏数据。

## 8. 二值信号量 (Binary Semaphore)

### 💡 核心机制
* **“旗帜”设计哲学**：二值信号量本质上是一个长度为 1 的队列，其核心作用是作为“旗帜”在任务与中断、任务与任务之间传递事件通知或同步，而不是用于资源保护。
* **初始状态为空**：通过 `xSemaphoreCreateBinary()` 创建后，其初始可用计数值为 0（即为 Empty/不可用状态）。接收端尝试 `Take` 会立即被阻塞，直到发送端（如中断或另一个任务）调用 `Give` 放入资源后，接收端才会被唤醒。
* **所有权无绑定**：二值信号量不属于任何特定任务。任何任务或中断都可以 `Give`，任何任务都可以 `Take`。因此可以安全地在中断服务程序（ISR）中通过 `xSemaphoreGiveFromISR` 释放。

### ⚠️ 避坑指南
* **中断调用 API 安全**：在中断中释放信号量必须使用带有 `FromISR` 后缀的 API（如 `xSemaphoreGiveFromISR`），并在退出中断前使用 `portYIELD_FROM_ISR` 执行必要的任务切换。
* **无优先级继承防反转**：二值信号量**不支持**优先级继承机制。因此，如果尝试将其用作保护共享资源的锁，当高优先级任务等待低优先级任务释放该信号量时，若中优先级任务就绪，会直接抢占低优先级任务运行，从而引发严重的**优先级反转（Priority Inversion）**。

## 9. 互斥量 (Mutex)

### 💡 核心机制
* **“锁”设计哲学**：互斥量是专为保护共享临界资源而设计的互斥访问机制（即“排他锁”）。
* **初始状态为满**：使用 `xSemaphoreCreateMutex()` 创建后，互斥量的初始可用计数值为 1（即为 Full/可用状态）。任何任务在访问共享资源前都可以直接成功 `Take`。
* **所有权绑定与“任务私有”**：互斥量具有强烈的“所有权”属性。哪个任务 `Take` 了这把锁，就必须由**同一个任务**来 `Give` 释放。锁的内部状态与获取锁的任务 ID/TCB 深度绑定。

### ⚠️ 避坑指南
* **禁止在中断中调用**：由于互斥量与任务句柄/TCB 紧密绑定，并包含导致任务阻塞/唤醒及优先级提权等一系列必须依赖任务上下文的操作，因此**绝对禁止在中断服务程序（ISR）中获取或释放互斥量**。
* **优先级继承机制**：当高优先级任务 H 因等待锁而被阻塞时，内核会自动将当前持有锁的低优先级任务 L 的优先级临时提升到与 H 相同的水平（优先级继承），防止中优先级任务 M 抢占 L，从而将优先级反转的影响降到最低。一旦 L 释放锁，其优先级会恢复原样。
* **自死锁与重入锁选择**：普通互斥量不支持在同一个任务内重复 `Take`（会导致获取失败或任务自我阻塞死锁）。若在递归函数或多层嵌套调用中需要对同一资源重复加锁，必须使用**递归互斥量（Recursive Mutex）**并配套使用 `xSemaphoreTakeRecursive` / `xSemaphoreGiveRecursive`。

## 10. 事件组 (Event Group)

### 💡 核心机制
* **多对多广播与多事件组合**：事件组使用 24 位（32 位 CPU 下）或 8 位（16 位 CPU 下）来代表不同的事件状态标志。它允许多个任务阻塞等待同一个事件组中的某些标志位。当标志位满足预设的 AND 或 OR 条件时，内核会**同时唤醒所有**阻塞在该条件上的就绪任务，实现“一对多/多对多”的广播式同步。
* **按位清除（xClearOnExit）**：在调用 `xEventGroupWaitBits()` 时若设置 `xClearOnExit` 为 `pdTRUE`，当任务被成功唤醒并返回前，内核会**仅自动清除在 `uxBitsToWaitFor` 中指定的那些标志位**，其余未指定位不受影响。
* **同步屏障（Sync Barrier / Rendezvous）**：
  * 使用 `xEventGroupSync(xEventGroup, uxBitsToSet, uxBitsToWaitFor, xTicksToWait)` 接口可以让多个任务在同一个点进行协同对齐。
  * 每个任务在到达同步点时置位自己的标志位（`uxBitsToSet`），并进入阻塞等待（`uxBitsToWaitFor` 所有参与任务的标志位均就绪）。只有当所有任务都到达该屏障点时，它们才会被同时唤醒，并自动清除标志位，携手进入下一阶段的工作。

### ⚠️ 避坑指南
* **中断中设置标志的“两步式”非确定性机制**：
  * 绝对**不能**直接在中断里同步更新事件标志，因为置位事件标志可能会触发多个任务的优先级判定与状态切换，这是一个非确定性时间（Non-deterministic）的操作，如果在 ISR 中直接执行会破坏硬实时中断的响应。
  * 在中断中必须使用 `xEventGroupSetBitsFromISR()`。该函数并不会在中断中直接改变事件位，而是**向 FreeRTOS 定时器后台任务（Daemon Task）发送一条消息**，委托该高优先级任务（优先级通常由 `configTIMER_TASK_PRIORITY` 定义）在中断退出后异步执行真正的置位操作。
  * **使用前提**：由于依赖定时器任务，系统必须在 `FreeRTOSConfig.h` 中配置 `configUSE_TIMERS` 为 1，且 `configTIMER_QUEUE_LENGTH` 队列长度足够大。
