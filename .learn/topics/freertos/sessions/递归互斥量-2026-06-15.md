## Positioning

递归互斥量位于 **同步机制 → 递归互斥量** 分支。它是一种特殊的互斥量，专门用于解决“同一任务多次获取同一把锁”时导致的死锁问题。

## Analogy

想像有一间带锁的私人办公室。
* **普通互斥量 (Mutex)**：规定“只要门是锁着的，任何人（包括刚刚锁门的人）都不能再进”。如果你锁了门，进入房间后，由于某些原因你又想通过另一道内部安全门（需要同一把钥匙锁），你重新申请这把钥匙，结果发现“钥匙已被占用”，你就把自己锁死在里面了。
* **递归互斥量 (Recursive Mutex)**：认人不认锁。它知道当前是谁持有了这把钥匙。如果你（当前任务）已经拿到了钥匙，再次申请时，它直接放行，只是把“进入深度”（计数器）加 1。你出来时必须同样出来相同次数（解开相同次数的锁），办公室门才会重新对其他人开放。

## Core Mechanism

在 FreeRTOS 中，普通的 Mutex 不允许同一个任务重复 `Take`。如果一个任务在持有普通 Mutex 的情况下再次尝试 `Take` 该 Mutex，任务会因为等待自己释放锁而进入无限阻塞（死锁）。

为了支持重入（Reentrancy）或递归函数调用，FreeRTOS 提供了**递归互斥量**：
1. **拥有者跟踪**：内核会记录当前持有互斥量的任务句柄。
2. **嵌套计数**：如果同一个任务再次获取锁，内核只递增一个计数器，而不会阻塞任务。
3. **配对释放**：任务 `Take` 了多少次，就必须 `Give` 多少次。只有当计数归零时，互斥量才真正释放，其他任务才能获取。

API 对比：
* 普通互斥量：`xSemaphoreCreateMutex()`, `xSemaphoreTake()`, `xSemaphoreGive()`
* 递归互斥量：`xSemaphoreCreateRecursiveMutex()`, `xSemaphoreTakeRecursive()`, `xSemaphoreGiveRecursive()`
> *注意：递归互斥量必须在 `FreeRTOSConfig.h` 中配置 `configUSE_RECURSIVE_MUTEXES` 为 1。*

## Code Example

在 [starter.c](file:///C:/Users/24212/Desktop/za/study/learn-anything/01-FreeRTOS-LED/User/starter.c#L164-L246) 中，我们已经准备了递归互斥量的经典演示代码：

```c
static SemaphoreHandle_t xRecMutex = NULL;

/* 模拟一个"日志写入"场景 */
static void log_write(const char *str)
{
    printf("%s", str);
}

static void log_write_line(const char *tag, int value)
{
    // 获取递归互斥量
    xSemaphoreTakeRecursive(xRecMutex, portMAX_DELAY);

    char buf[32];
    sprintf(buf, "[%s] %d\r\n", tag, value);
    log_write(buf);

    // 释放递归互斥量
    xSemaphoreGiveRecursive(xRecMutex);
}

/* 递归遍历打印任务链 — 模拟分层日志 */
static void print_task_chain(const char **names, int depth)
{
    // 第一次获取锁
    xSemaphoreTakeRecursive(xRecMutex, portMAX_DELAY);

    if (depth > 0) {
        /* 调用同样需要锁的格式化打印 */
        log_write_line(names[depth - 1], depth);  /* ← 递归获取！如果是普通 Mutex，这里就会发生死锁 */
        print_task_chain(names, depth - 1);        /* 递归调用 */
    }

    // 释放锁
    xSemaphoreGiveRecursive(xRecMutex);
}
```

### 代码解析：
1. `print_task_chain` 首先持有了 `xRecMutex`。
2. 随后它调用了 `log_write_line`，该函数内部也试图获取 `xRecMutex`。
3. 由于使用的是递归互斥量，`log_write_line` 能够成功获取锁并执行打印，不会死锁。

## Common Misconceptions

1. **认为普通 Mutex 可以通过编写“防死锁代码”代替递归互斥量**：在复杂的业务逻辑或深层嵌套回调中，人工去追踪锁的状态极其困难且容易出错，递归互斥量在架构设计上优雅地解决了这一问题。
2. **忘记成对释放**：如果 `Take` 了 3 次，但只 `Give` 了 2 次，这个互斥量将永远不会被释放，导致其他任务永久饿死。

## Quick Summary

- 递归互斥量允许同一个任务在不释放锁的情况下，多次获取（Take）同一把锁。
- 采用嵌套计数器管理，`Take` 和 `Give` 必须成对且次数相等才能真正释放锁。
- 主要用于**递归函数调用**或**多层嵌套的子系统函数**中保护同一个共享资源。

## Socratic Check & Discussion

* **Question**: 如果任务 A 调用了 3 次 `xSemaphoreTakeRecursive()` 成功获取了递归互斥量，但只调用了 2 次 `xSemaphoreGiveRecursive()`。此时，如果有另一个优先级更高的任务 B 尝试获取这把锁，会发生什么？任务 A 的优先级在此刻会受影响吗？
* **User's Answer & Discussion**:
  1. 任务 B 无法获取锁并进入阻塞状态（因为嵌套计数未归零，锁未完全释放）。
  2. 任务 A 的优先级**会受到影响**。由于递归互斥量继承了 Mutex 的**优先级继承 (Priority Inheritance)** 特性，任务 A 的优先级会临时提升到与任务 B 相同的优先级，以防止优先级反转。当任务 A 完成第 3 次 `Give` 完全释放锁后，其优先级会恢复至原优先级，任务 B 获得锁并抢占运行。
